# پرو مجازی، تاریخچه خصوصی و بررسی محصول

این قابلیت توسعهٔ همان React/Vite و Express/MySQL موجود است. سرویس اصلی با قرارداد multipart شامل فقط person و cloth حفظ شده است. خروجی نمونه، سرویس جایگزین ساختگی یا درصد مبتنی بر تایمر در کد تولید وجود ندارد. پاسخ‌های کنترل‌شده فقط در پوشه‌های test و e2e قرار دارند.

## وضعیت و مصرف اعتبار

POST معتبر پس از اعتبارسنجی محتوا، محصول عمومی و فروشندهٔ تأییدشده، یک عملیات پایدار با شناسهٔ تصادفی و Idempotency Key ایجاد می‌کند. رزرو اعتبار زیر قفل ردیف همان فروشنده انجام می‌شود. مشتری هزینه یا محدودیت شخصی ندارد؛ موجودی همان فروشگاه پرداخت‌کننده است.

مرحلهٔ ۱، اعتبارسنجی و ذخیرهٔ ورودی، یک مرحلهٔ تکمیل‌شده از چهار مرحله است (۲۵٪). پردازش AI درصد واقعی ندارد و به‌صورت نامعین نشان داده می‌شود. دریافت نتیجه و ثبت فایل مراحل ۳ و ۴ هستند (۵۰ و ۷۵٪). فقط پس از ثبت تراکنشی مصرف، خروجی و وضعیت completed مقدار ۱۰۰٪ نمایش داده می‌شود. نوار در محل دکمه و بدون Modal پردازش قرار دارد.

صف SQL با یک worker در همان فرایند Node اجرا می‌شود؛ lease و heartbeat از اجرای هم‌زمان جلوگیری می‌کنند. راه‌اندازی دوباره، خروجی ذخیره‌شده یا مرجع رمز‌شدهٔ فایل دریافتی را بازیابی می‌کند. manifest خصوصی قبل از ثبت فایل در دیتابیس، پاسخ موفق را برای بازیابی نگه می‌دارد. فایل قبل از نهایی‌شدن مصرف به مشتری تحویل داده نمی‌شود.

Timeout یا قطع ارتباط پس از ارسال درخواست ممکن است به معنی اجرای ادامه‌دار سرویس خارجی باشد. چنین عملیاتی نیازمند پیگیری است و خودکار دوباره ارسال نمی‌شود. حذف عکس‌های این عملیات نیز سد تشخیص ورودی تکراری را حذف نمی‌کند. لغو واقعی توسط API فعلی پشتیبانی نمی‌شود؛ رابط لغو نمایشی اضافه نشده است.

## مالکیت و حریم خصوصی

- حساب واردشده: مالکیت بر اساس شناسهٔ معتبر حساب در سرور.
- بازدیدکنندهٔ مهمان: نشست امضاشدهٔ HttpOnly و SameSite؛ کوکی تولید با پیشوند __Host- و Secure است. سوابق مهمان به همان مرورگر وابسته است و با پاک‌کردن کوکی یا تغییر دستگاه بازیابی نمی‌شود.
- IP، شناسهٔ فروشندهٔ پرداخت‌کننده یا شناسهٔ محصول، مدرک مالکیت عکس محسوب نمی‌شوند.
- سابقهٔ ناشناس قدیمی که مالک قابل‌اثبات ندارد، حفظ و فقط در مدیریت قابل بررسی است. به کاربر یا فروشنده‌ای بر اساس IP نسبت داده نمی‌شود.
- تصاویر جدید خارج از web root و با مجوزهای 0700/0600 نگهداری می‌شوند. URL عمومی به فایل خصوصی وجود ندارد.
- در صفحهٔ پرو، چک‌باکس‌های رضایت تکراری و دکمه‌های حذف سابقه وجود ندارند؛ مشاهده، دانلود و صفحه‌بندی سوابق حفظ شده‌اند. API حذف مالک برای سازگاری مسیرهای قبلی و فرایند حذف حساب حفظ شده است.
- مهمان پیش از اولین ساخت خروجی، قوانین پرو را تأیید می‌کند؛ پذیرش نسخهٔ جاری به هش نشست امضاشده در سرور متصل است. انصراف یا شکست ثبت پذیرش، عملیات یا مصرف اعتبار ایجاد نمی‌کند. نشست تازه، منقضی یا باطل‌شده پذیرش نشست دیگر را به ارث نمی‌برد.
- رسید مهمان در virtual_tryon_terms_acceptances با مهلت ۱۸۰ روز و تمدید هنگام استفاده نگهداری می‌شود. پاک‌سازی رسید منقضی، تصاویر و تاریخچه را حذف نمی‌کند. زمان واقعی پذیرش و نسخهٔ آن در عملیات ثبت می‌شود. حساب واردشده طبق تصمیم مالک سامانه از قوانین ثبت‌نام استفاده می‌کند؛ processing_consent_at آن null است تا زمان تاریخی تأیید جعل نشود و privacy_version منبع registration-policy را مشخص می‌کند.
- صفحهٔ فعلی diagnostics_consent=false ارسال می‌کند و اطلاعات دستگاه/IP را جمع‌آوری نمی‌کند. قرارداد تشخیص اختیاری کلاینت‌های قبلی همچنان به رضایت مستقل نیاز دارد؛ اطلاعات موجود پس از ۷ روز از دیتابیس فعال پاک می‌شود. مدل دقیق دستگاه حدس زده نمی‌شود.
- تشخیص IP فقط پشت proxy لوپ‌بکِ مورد اعتماد انجام می‌شود؛ هدر مرورگر به‌تنهایی معتبر نیست.
- حذف حساب، دسترسی به عکس‌های همان حساب را می‌بندد و پاک‌سازی فایل‌های آن را در چرخهٔ worker انجام می‌دهد. دادهٔ مشتریِ مستقل با حذف حساب فروشنده به فروشندهٔ دیگر منتقل نمی‌شود.
- دسترسی مدیر به فهرست، جزئیات و تصاویر و تغییر تنظیمات در virtual_tryon_audit ثبت می‌شود. صفحات جدید یا APIهای فروشنده اطلاعات دستگاه و IP دیگران را دریافت نمی‌کنند.
- لاگ access مربوط به مسیرهای خصوصی پرو در Nginx و Morgan غیرفعال است؛ ثبت اختیاری diagnostics با لاگ فنی مستقل اشتباه گرفته نمی‌شود.
- حذف از دیتابیس/ذخیره‌سازی فعال، نسخه‌های پشتیبان قدیمی را ویرایش نمی‌کند. چرخه و حذف بکاپ‌های موجود تابع سیاست عملیاتی مالک سرور است؛ این نسخه برای حذف خودکار آن بکاپ‌ها مجوز تازه‌ای فرض نمی‌کند.

## API

تمام مسیرهای زیر با همان envelope موفقیت و خطای موجود پاسخ می‌دهند. تصاویر attachment یا inline با Content-Type واقعی، no-store و nosniff ارسال می‌شوند.

| مسیر | کاربرد و دسترسی |
|---|---|
| GET /api/tryon/terms | نسخه و متن قوانین و ضرورت تأیید برای همان حساب/نشست؛ private/no-store |
| POST /api/tryon/terms | ثبت یک‌باره با accepted=true و version جاری؛ محافظت Origin و محدودیت نرخ؛ مالک فقط از نشست سرور |
| POST /api/stores/:slug/products/:productId/pro/jobs | شروع برای حساب/نشست خصوصی؛ image، image_index و request_key؛ مهمان نیازمند پذیرش معتبر است (428 در غیر این صورت)؛ processing_consent=true کلاینت قبلی نیز سازگار است |
| GET /api/tryon/by-request/:key | بازیابی پاسخ گم‌شدهٔ همان درخواست و همان مالک |
| GET /api/tryon/jobs/:id | وضعیت عملیات متعلق به مالک |
| POST /api/tryon/jobs/:id/retry | تلاش مجدد کنترل‌شده با request_key جدید |
| DELETE /api/tryon/jobs/:id | حذف عکس‌های عملیات پایان‌یافتهٔ همان مالک |
| GET /api/tryon/history?page=&limit= | آخرین موفق، عملیات فعال مستقل و صفحهٔ موارد قبلی |
| GET /api/tryon/jobs/:id/images/:kind?download=1 | ورودی، محصول یا خروجی؛ مالکیت در سرور |
| GET /api/admin/tryon/jobs | فیلتر q، status، provider، from، to و صفحه‌بندی در سرور |
| GET /api/admin/tryon/jobs/:id | جزئیات، تلاش‌ها، تصاویر و diagnostics مجاز؛ فقط Admin فعال |
| GET /api/admin/tryon/jobs/:id/images/:kind?download=1 | دانلود مدیریتی با Audit |
| GET /api/admin/tryon/providers | تنظیمات عمومی و وضعیت وجود کلید؛ بدون مقدار کلید |
| PUT /api/admin/tryon/providers/:id | ذخیرهٔ جایگاه ۱ تا ۳، رمزگذاری کلید در Backend |
| POST /api/admin/tryon/providers/:id/test | بررسی دسترسی شبکه/قرارداد؛ به معنی آزمون تولید تصویر نیست |
| GET /api/admin/products/:id/review | جزئیات و توکن همان نسخهٔ محصول |
| GET /api/admin/products/:id/images/:index | پیش‌نمایش/دانلود معتبر همان نسخهٔ جاری یا پیشنهادی |
| PATCH /api/admin/products/:id/approve یا reject | review_token و revision اجباری؛ رد نیازمند reason_id معتبر و توضیح لازم |
| GET /api/admin/products/:id/review-history | تاریخچهٔ تصمیم‌ها با صفحه‌بندی |
| GET /api/seller/products/:id/review-history | فقط مالک همان محصول |
| GET/POST/PATCH /api/admin/product-rejection-reasons[/id] | مدیریت دلایل ساختاری رد |

مسیرهای قدیمی /pro-api/try-on، /m1، /m2 و pro/upload، pro/use و pro/history از همان مرز مالکیت/عملیات عبور می‌کنند. URL قدیمی /api/pro-output فقط برای خروجی قدیمیِ قابل اثبات همان مالک معتبر است؛ proxy عمومی URL وجود ندارد. موجودبودن مسیر alias به معنی پشتیبانی آن در سرویس خارجی نیست.

## سرویس‌های جایگزین

جایگاه اول از تنظیم واقعی موجود seed می‌شود و در اجرای بعدی overwrite نمی‌شود. دو جایگاه دیگر تا تنظیم مدیر غیرفعال/تعریف‌نشده می‌مانند.

Adapterهای پشتیبانی‌شده: rookhposh_multipart، multipart، json_images و openai_edit. پارامترها محدود و اعتبارسنجی‌شده‌اند. ترتیب با priority و id تعیین می‌شود. پاسخ موفق دیگر سرویس‌ها را متوقف می‌کند. خطای ورودی/ایمنی failover ندارد. خطای احراز هویت cooldown و اعلان مدیریتی دارد. 429 با Retry-After و خطاهای شبکه/5xx قابل‌بازیابی مدیریت می‌شوند؛ تلاش و timeout محدود است. هزینهٔ خارجی فقط در صورت دادهٔ معتبر قابل ثبت است و از روی زمان یا حدس ساخته نمی‌شود.

Endpoint جدید باید HTTPS عمومی و بدون کلید در URL باشد. DNS، همهٔ آدرس‌های حل‌شده، تغییر مسیر، اندازهٔ پاسخ و مقصد نهایی بررسی می‌شوند؛ اتصال به IP تأییدشده pin می‌شود. آدرس HTTP سرویس موجود فقط به‌عنوان استثنای دقیق سازگاری حفظ شده است. این استثنا رمزگذاری انتقال شبکه به سرویس خارجی را ایجاد نمی‌کند؛ فعال‌سازی TLS آن به زیرساخت خود ارائه‌دهنده نیاز دارد.

## تنظیم و استقرار

TRYON_SECRET_KEY باید قبل از راه‌اندازی production مقدار تصادفی حداقل ۳۲ کاراکتری داشته باشد. برنامه پیش از readiness در نبود آن متوقف می‌شود. این کلید را همراه بکاپ محرمانه نگه دارید؛ تغییر آن بدون بازرمزگذاری کلیدها و manifestها مجاز نیست.

TRYON_STORAGE_ROOT باید خارج از public root، متعلق به کاربر برنامه و 0700 باشد؛ مسیر پیشنهادی /var/lib/rookhposh-dash/tryon است. هیچ مقدار محرمانه در فرانت‌اند یا Git ذخیره نشود.

در سرویس دارای ProtectSystem=strict، فایل deploy/systemd/tryon-storage.conf را به‌عنوان drop-in همان سرویس نصب کنید تا فقط همین پوشهٔ خصوصی قابل نوشتن شود. ابتدا پوشه را با مالک برنامه و مجوز 0700 بسازید؛ مجوزهای سایر مسیرها تغییر نکنند.

Migration در runtimeSetup موجود افزایشی است: چهار جدول عملیات/فایل/تلاش/سرویس و Audit، سه جدول بررسی محصول و ستون‌ها/ایندکس‌های لازم اضافه می‌شوند. دادهٔ اصلی و تاریخچهٔ قدیمی حذف نمی‌شوند. سوابق قدیمی backfill و ناشناس‌های فاقد مالک صریحاً legacy می‌شوند. تکرار migration داده را تکثیر نمی‌کند.

tryonTermsSchema فقط جدول پذیرش قوانین را اضافه می‌کند و داده‌های قبلی را تغییر نمی‌دهد. rollback مستقل یا کامل در حضور رسید پذیرش از حذف آن خودداری می‌کند؛ rollback جدول خالی قابل اجراست.

rollbackTryon یک down محافظت‌شده برای دیتابیس بدون دادهٔ عملیاتی جدید دارد و در حضور داده یا تنظیمات جدید از حذف جلوگیری می‌کند. پس از ثبت عملیات، schema و فایل‌های خصوصی را حفظ و نسخهٔ سازگار بعدی منتشر کنید. برای بازگشت اضطراری به backend قدیمی، ابتدا همهٔ مسیرهای پرو/تاریخچهٔ قدیمی را پشت maintenance امن ببندید تا کنترل مالکیت دوباره باز نشود. بازگرداندن کورکورانهٔ dump قدیمی داده‌های تازه را از بین می‌برد و مجاز نیست.

پیش از جابه‌جایی backend، درخواست‌های قبلی را drain کنید. worker و برنامهٔ قدیمی نباید هم‌زمان مصرف اعتبار را با دو قرارداد متفاوت ثبت کنند. بکاپ دیتابیس، سورس، build، تنظیمات خصوصی و فایل‌های خصوصی را با checksum بگیرید. سایت اصلی، CMS، DNS و سرویس بانکی/پیامکی دیگر را تغییر ندهید.

## اعتبارسنجی قابل تکرار

npm run lint، npm run test:unit و npm run build. پروژه JavaScript است و فرمان TypeScript typecheck مستقل ندارد.

تست‌های integration فقط NODE_ENV=test و DB_NAME با پیشوند rookhposh_payment_test_ را می‌پذیرند. schema اصلی باید در دیتابیس یکبارمصرف وارد شود؛ سپس test:tryon:integration، test:reviews:integration و suiteهای پرداخت/اعتبار/مالی اجرا شوند. هر suite دیتابیس مستقل می‌خواهد.

test:tryon-terms:integration پذیرش یک‌باره، نبود مصرف قبل از پذیرش، درخواست هم‌زمان، جداسازی نشست، CSRF، نسخه نامعتبر، انقضا، ابطال، قرارداد قبلی و rollback محافظت‌شده را بررسی می‌کند. e2e/root-cause-terms.spec.cjs با fixture یکبارمصرف، جریان تأیید/انصراف/خطا، قفل ورودی‌ها، عدم تکرار پس از reload، نبود حذف و دانلود فایل واقعی جدید و قبلی را در چهار اندازهٔ نمایش تست می‌کند.

سرور e2e فقط در همین دیتابیس یکبارمصرف قابل اجراست: backend/test/helpers/tryonE2EServer.js با E2E_METADATA و E2E_PORT. آن را صرفاً به لوپ‌بک bind می‌کند. برنامه واقعی، ذخیره خصوصی، دیتابیس و دانلود واقعی اجرا می‌شوند؛ پاسخ AI در این fixture عمداً کنترل‌شده است و به معنی تأیید سرویس خارجی نیست. پس از Build، E2E_BASE_URL و E2E_METADATA را به playwright.config.cjs بدهید؛ Chrome، Firefox، WebKit و اندازه‌های موبایل تعریف شده‌اند. WebKit معادل تست دستگاه واقعی Safari نیست.

گزارش اجرای واقعی باید نتیجهٔ generation سرویس موجود را جدا از connection test و تست‌های controlled failover اعلام کند.
